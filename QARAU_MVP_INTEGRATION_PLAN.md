# QARAU MVP — detailed integration plan

Plan date: 2026-09-05  
Input: [`QARAU_MVP_GAP_AUDIT.md`](QARAU_MVP_GAP_AUDIT.md) and the supplied QARAU MVP requirements  
Integration strategy: incremental replacement around the working prototype; no rewrite and no mock marketplace state

## 1. Goal and completion boundary

The integration is complete only when the existing research prototype can execute this real path:

`discovery → fetch → immutable raw snapshot → normalization → dataset version → target mapping → persisted signals → temporal validation → deterministic Alpha Score → sealed package → DatasetCommitment PDA → Sale PDA → buyer-signed SOL payment → AccessGrant PDA → protected tier-aware delivery → Proof-of-Alpha verification`

The following do not count as completion:

- a database flag that substitutes for on-chain seats or grants;
- a Memo instruction that substitutes for DatasetCommitment;
- a prepared JSON file shown as a scrape;
- a wallet public key accepted without a signature;
- a successful transaction signature that has not been confirmed and decoded;
- a UI label for access tier that does not change the bytes a user can retrieve;
- an analysis score generated by an LLM or selected using the final test period.

## 2. Integration principles

1. **Preserve the working prototype.** Keep existing discovery, provider adapters, owner auth, SSRF protection, parser limits, analysis tests, encryption code, and UI pages until their replacements pass equivalent tests.
2. **Strangler migration.** Introduce repository/storage/job interfaces behind `QarauService`; move one workflow at a time from the encrypted state file to durable services.
3. **One authority per fact.** Solana owns commitment hashes, sale state, seat count, and grants. PostgreSQL owns workflow metadata. Object storage owns immutable artifact bytes.
4. **Hash exact stored bytes.** Verification loads and hashes the committed artifact; it never regenerates an allegedly equivalent file from mutable database rows.
5. **Chain reads authorize; cache reads do not.** Database grant/sale records are reconciliation caches and indexes only.
6. **Buyer keys stay in the wallet.** The backend signer performs publisher operations only. It never signs purchases for buyers.
7. **Every long operation is a durable job.** API requests enqueue and return; workers fetch, normalize, analyze, publish, or reconcile.
8. **No sale before validation is sealed.** Package publication is downstream of an immutable DatasetVersion and completed AnalysisRun.
9. **Default-deny delivery.** Missing, stale, malformed, expired, mismatched, or unreadable on-chain access state returns 403/503, never the data.
10. **MVP scope stays narrow.** Devnet, SOL payment, one crypto target adapter, the current traditional target path, fixed-price timed sale, and two access tiers.

## 3. Decisions to freeze before implementation

These are contract decisions. Changing them after database migrations, artifact publication, or program deployment is costly.

| ID | Decision | Proposed MVP choice | Reversibility |
|---|---|---|---|
| D-01 | Payment asset | Native SOL only; USDC postponed | Costly but additive |
| D-02 | Sale type | Timed fixed-price sale with minimum/fixed price; no bidding engine | Additive |
| D-03 | Network | Local validator for tests, Devnet for live acceptance | Reversible by config |
| D-04 | Wallet auth | SIWS with server nonce; legacy `signMessage` fallback only if it verifies the same bound fields | Costly public contract |
| D-05 | Database | PostgreSQL with explicit SQL migrations | Costly migration |
| D-06 | Job queue | PostgreSQL-backed at-least-once durable queue using row leases/heartbeats; separate idempotent workers | Replaceable behind interface |
| D-07 | Artifact store | Private S3-compatible object storage with storage-side encryption and backend-only streaming; MinIO-compatible local development | Replaceable behind interface |
| D-08 | Commitment artifact | Canonical uncompressed JSON/JSONL bytes; optional Parquet is a non-authoritative derivative | One-way after publication |
| D-09 | Dataset identity | UUID off-chain; SHA-256 UUID/domain digest as fixed `[u8;32]` on-chain ID | One-way after deployment |
| D-10 | Version type | Monotonic `u32`, scoped to dataset | One-way after deployment |
| D-11 | Access tiers | `EXCLUSIVE_EARLY` and `DELAYED`; program stores policy primitives and `access_policy_hash`, backend hash-verifies and evaluates the immutable policy | One-way policy contract |
| D-12 | Grant scope | Dataset line + purchased DatasetCommitment/version + buyer wallet; cross-version visibility is bounded by the committed policy | One-way after deployment |
| D-13 | Program upgrade | Upgradeable on Devnet with multisig/runbook target; do not mark immutable during MVP | Operationally costly |
| D-14 | Package gate | Completed validation, no blocking leakage, minimum sample size; Alpha threshold configured and formula-versioned | Reversible for new packages |
| D-15 | Commitment level | `confirmed` means payment observed in UI; only `finalized` state may authorize irreversible private-data delivery | Reversible by config |
| D-16 | Quantitative contract | Exact formulas, thresholds, annualization, regimes, multiple-testing method, and golden outputs frozen before signal implementation | Costly research contract |

Human checkpoints are required before D-08 through D-12 and D-16 are implemented because they define published hashes, PDA addresses, grant semantics, and the meaning of a reported Alpha Score.

## 4. Target runtime topology

### 4.1 Processes

| Process | Responsibility | May access publisher key? | May access artifact plaintext? |
|---|---|---:|---:|
| `api` | Owner/buyer APIs, sessions, transaction building, protected delivery | No | Only authorized streaming paths |
| `worker-discovery` | Query generation, search, candidate classification | No | No dataset artifacts |
| `worker-scrape` | Fetch, raw capture, parsing, source health | No | Raw source artifacts |
| `worker-analysis` | Normalize, construct signals, validate, score, package artifacts | No | Dataset and analysis artifacts |
| `scheduler` | Enqueue due scrapes/reconciliation; no heavy work | No | No |
| `worker-chain` | Publish commitments/sales, reconcile transactions/accounts | Through isolated signer RPC only | Hashes/manifests, not raw datasets |
| `publisher-signer` | Validate narrow publisher intent and sign allowed program instructions | Yes | No |

`publisher-signer` is a separate service/container, not a child process of the API or chain worker. Only this service receives the operational publisher key mount. Deployment/upgrade authority is stored separately and is never mounted into the running application topology.

### 4.2 Infrastructure

- PostgreSQL: authoritative off-chain metadata, jobs, sessions/nonces, audits, and chain caches.
- Private object storage: raw, normalized, analysis, package, and export artifacts.
- Solana local validator: program integration tests.
- Solana Devnet RPC: live acceptance and demo.
- Existing Vite/React frontend: owner research UI plus new marketplace/wallet views.

### 4.3 Local compose target

Extend `compose.yaml` with:

- `postgres` and a health check;
- `object-storage` and a private bucket initialization job;
- `api`;
- `worker-discovery`;
- `worker-scrape`;
- `worker-analysis`;
- `worker-chain`;
- `scheduler`.
- `publisher-signer` on a private authenticated service boundary.

Application containers may share a base image but receive least-privilege credentials per role; they do not share a universal environment file. Only `api` is publicly exposed. PostgreSQL, object storage, and publisher signer stay on the private compose network.

### 6.2 Dataset versioning

#### `datasets`

- `id uuid primary key`, `source_id uuid references sources`
- `name text`, `semantic_schema jsonb`
- `current_version integer`
- unique logical dataset identity independent from scrape attempts

#### `dataset_versions`

- `id uuid primary key`, `dataset_id uuid references datasets`
- `source_snapshot_id uuid not null unique references source_snapshots`
- `version integer not null`
- `status enum(allocated,normalizing,uploading,stored,sealed,failed)`
- `normalized_object_key text`, `normalized_hash bytea`
- `schema_profile jsonb`, `quality_metrics jsonb`
- `coverage_start`, `coverage_end`, `frequency`
- `record_count`, `missing_rate`, `duplicate_rate`, `outlier_rate`, `continuity`
- `normalizer_version text`, `created_at`
- unique `(dataset_id, version)`

Every successful scrape creates DatasetVersion N+1, including a `NO_CHANGE` result. A no-change version may reference the same content-addressed normalized object/hash as version N, but it remains a distinct immutable version linked to the new raw SourceSnapshot. This satisfies both change detection and the requirement that a repeat scrape never overwrites the prior version.

The MVP enforces exactly one SourceSnapshot per DatasetVersion, matching the current one-source dataset model and keeping `raw_snapshot_hash` unambiguous. Multi-source datasets require a future canonical ordered source-manifest contract and are out of scope for V1.

Canonical state transitions are `ALLOCATED → NORMALIZING → UPLOADING → STORED → SEALED`. Any pre-sealed state may transition to `FAILED` with a linked PipelineStageRun error; `SEALED` is terminal and immutable.

## 7. Artifact contracts

### 7.1 Object layout

```text
raw/{source_id}/{snapshot_id}/response-body.bin
raw/{source_id}/{snapshot_id}/manifest.json
normalized/{dataset_id}/v{version}/data.jsonl
normalized/{dataset_id}/v{version}/schema.json
analysis/{analysis_id}/signals/{signal_id}.jsonl
analysis/{analysis_id}/manifest.json
analysis/{analysis_id}/results.json
analysis/{analysis_id}/report.json
packages/{package_id}/public-metadata.json
packages/{package_id}/private-metadata.json
packages/{package_id}/access-policy.json
packages/{package_id}/exports/data.csv
```

Bucket listing is private. Storage-side encryption protects objects at rest. Canonical plaintext artifact bytes are hashed, and only the backend can retrieve and stream them after authorization. Object keys and signed storage URLs never appear in public or buyer API responses.

### 7.2 Canonical normalized JSONL

- UTF-8, no BOM, LF line endings.
- One RFC 8785/JCS-compatible object per line.
- Keys ordered by the canonical JSON algorithm.
- Timestamps UTC ISO-8601 with millisecond precision.
- Measurement values use canonical decimal strings under a schema-declared precision/scale rule: no exponent, no leading plus/zeros, trailing fractional zeros removed, and `-0` normalized to `0`. Derived binary floating-point metrics appear only in JCS analysis result artifacts. NaN and infinities are forbidden.
- Missing fields represented consistently according to schema, not omitted unpredictably.
- Rows sorted by primary timestamp and deterministic tie-breaker.
- Final newline required.

Hash the exact canonical uncompressed bytes with a versioned domain prefix. Compressed delivery files and Parquet derivatives get their own non-authoritative hashes. Store golden byte fixtures—not only expected digests—for key ordering, Unicode, UUID bytes, decimals, `-0`, timestamps, domain separators, and little-endian version encoding.

### 7.3 Analysis manifest

The manifest contains:

- dataset ID/version and raw/normalized hashes;
- market target/mapping and market snapshot hash;
- exact signal definitions and feature parameters;
- timestamp alignment/as-of join policy;
- train/validation/test boundaries;
- purge/embargo interval;
- regime definitions;
- screening universe and multiple-testing method;
- selected candidate and selection rule;
- quality/leakage gates;
- score formula/version and weights;
- code revision and dependency lock digest;
- pipeline configuration and deterministic seed, if used;
- no wall-clock creation/completion timestamps or execution IDs.

The canonical manifest is deterministic replay input. `analysis_runs` stores execution ID, start/completion times, environment, and rerun lineage outside the hashed manifest. A rerun uses the original canonical manifest bytes and produces a separate execution record, allowing the manifest hash and result hash to remain reproducible.

### 7.4 Hash domains

Use distinct prefixes such as:

- `QARAU_RAW_SNAPSHOT_V1\0`
- `QARAU_NORMALIZED_DATASET_V1\0`
- `QARAU_ANALYSIS_MANIFEST_V1\0`
- `QARAU_ANALYSIS_RESULT_V1\0`
- `QARAU_ACCESS_POLICY_V1\0`

The program receives the four required 32-byte dataset/analysis hashes plus one 32-byte access-policy hash. The API returns hexadecimal representations but decodes and compares bytes, not strings with flexible casing.

## 8. Quantitative pipeline integration

### 8.1 Normalization stages

1. Infer columns and primitive datatypes.
2. Select timestamp and availability timestamp with confidence/provenance.
3. Normalize timestamps to UTC; preserve the original text in raw artifacts only.
4. Detect measurement units and apply explicit conversions from a versioned registry.
5. Profile missingness, duplicates, impossible bounds, robust outliers, stale runs, gaps, frequency, and continuity.
6. Profile missingness by rolling/time windows and measure stability/drift; detect duplicated information across columns/signals using exact fingerprints and bounded correlation/redundancy rules.
7. Apply deterministic deduplication and field mapping rules.
8. Write canonical normalized artifact and schema profile.
9. Compare with the prior version and classify change.
10. Seal the DatasetVersion only after the artifact hash is persisted successfully.

The fetch boundary stores HTTP response-body entity bytes after transfer/content decoding performed by the HTTP stack but before charset decoding or parsing. `raw_snapshot_hash` is computed over those exact bytes plus its domain prefix. Parser input decoding, selected charset, and decoding errors are recorded separately.

Version sealing crosses PostgreSQL and object storage without pretending they share a transaction:

1. Allocate N+1 under a dataset-scoped advisory/row lock in state `ALLOCATED`, then enter `NORMALIZING`.
2. Canonicalize and hash bytes, enter `UPLOADING`, and use a deterministic content-addressed key.
3. Conditional-put the object, then `HEAD` it and verify size/hash metadata.
4. Mark `STORED`, link the SourceSnapshot, then transition to immutable `SEALED` in a database transaction.
5. An orphan sweeper removes unreferenced temporary objects after a safety window.

A `NO_CHANGE` scrape still creates N+1 as required, but may reference the already verified content-addressed normalized object. It never rewrites N.

Unknown units, ambiguous timestamps, or unverified publication latency must produce a warning and cap quality/Alpha Score; severe ambiguity blocks packaging.

### 8.2 Signal factory

For every approved numeric variable create persisted definitions for:

- raw value;
- absolute delta and percentage change;
- rolling change;
- rolling mean;
- rolling z-score;
- deviation from rolling mean;
- lagged variants for a frequency-specific bounded lag set.

Do not materialize every Cartesian product blindly. Store definitions first, apply bounded eligibility rules, and materialize only screened candidates. Every signal fingerprint includes source column, transformation, window, lag, imputation rule, winsorization rule, and pipeline version.

### 8.3 Market alignment

- Use backward/as-of joins against `available_at`, never observation timestamp alone.
- Never forward-fill across a publication boundary not known at prediction time.
- Normalize daily crypto and traditional calendars explicitly; record whether weekends are dropped or aligned.
- Compute forward returns only after feature availability has been frozen.
- Retain joined sample timestamps as an artifact so leakage review is reproducible.

### 8.4 Split and selection contract

1. Chronological train period: generate/fit transformations and screen candidates.
2. Chronological validation period: choose only among the candidate universe frozen by train screening, select transformation/lag/horizon, and freeze thresholds.
3. Untouched chronological test period: compute final OOS metrics exactly once per sealed manifest.
4. Purge and embargo overlapping return horizons at split boundaries.
5. Report train, validation, and test separately.
6. Split the test period into at least three named temporal regimes without using regime results to re-select the signal.

All imputation, scaling, winsorization, transform windows, selection thresholds, and score-calibration curves are fitted without test data. Trailing transforms use historical observations only. Backward as-of joins enforce a frequency-specific maximum staleness. Low-frequency signals are not duplicated into apparently independent daily samples: align the target to signal frequency or use documented effective-sample-size/HAC treatment. Overlapping horizons require purge/embargo and overlap-robust inference. Equity adapters use an explicit point-in-time corporate-action policy; adjusted history that could incorporate future actions cannot enter a publishable run without review. Assumed provider latency remains `UNVERIFIED` and blocks or caps publishability according to D-16.

The current `runAlphaTest` selects best lag before its folds. Replace that behavior before presenting results as final OOS evidence.

### 8.5 Score contract

Store a formula version and component breakdown:

```text
Alpha Score =
  0.15 × Data Quality
  0.20 × Predictive Strength
  0.30 × Test OOS Performance
  0.20 × Robustness
  0.15 × Freshness
  − Leakage Penalty
```

The exact normalization curves and caps must be frozen in D-14. Suggested hard gates:

- blocking look-ahead or timestamp misalignment: package prohibited;
- final test observations below threshold: package prohibited;
- unverified latency: score cap;
- suspicious instantaneous correlation: manual review plus score cap;
- unstable sign across regimes: robustness penalty;
- multiple-testing q-value above threshold: predictive-strength penalty or rejection.

The LLM may explain the score but receives metrics only after calculation and cannot change any component.

Before INT-031, `docs/adr/0006-quantitative-contract.md` must define machine-testable formulas and golden outputs for quality metrics, staleness/outliers, each signal transform, screening statistics, q-value correction, split/purge/embargo rules, return spread, Sharpe annualization by frequency, trade counting, regime boundaries, score normalization curves, caps, and penalties. No executor may choose these ad hoc while implementing the engine.

- early and delayed prices in lamports;
- grant duration;
- delayed initial DatasetCommitment pubkey (required when Delayed tier is enabled);
- max and occupied seats;
- enabled-tier bitmask;
- status enum;
- bump.

PDA seeds: `b"sale"`, DatasetCommitment pubkey.

#### `AccessGrant`

- DatasetCommitment pubkey;
- Sale pubkey;
- buyer wallet;
- dataset ID hash and purchased version (also cross-checked through DatasetCommitment);
- tier enum;
- granted and expiry timestamps;
- status enum;
- purchase transaction reference is indexed off-chain; it need not be stored as a string in the account;
- bump.

PDA seeds: `b"grant"`, DatasetCommitment pubkey, buyer pubkey.

### 9.2 Instructions

#### `initialize`

- Requires authority signer.
- Creates Registry PDA once.
- Stores treasury and schema version.

#### `publish_dataset`

- Requires registry authority.
- Validates nonzero dataset/analysis/policy hashes, nonzero/max-bounded seats, supported access-policy primitives, and monotonic version policy off-chain plus unique PDA on-chain.
- Creates immutable DatasetCommitment.

#### `create_sale`

- Requires registry authority and matching DatasetCommitment publisher.
- Validates sale interval, tier mask, supported payment asset (`SOL` only in V1), nonzero price, treasury equality, and commitment active status.
- When Delayed is enabled, validates the supplied delayed-initial DatasetCommitment is active, belongs to the same dataset ID hash, has the policy-selected earlier version, and is owned by this program.
- Requires Sale grant duration to equal DatasetCommitment's committed grant duration and copies it with max seats into Sale to make purchase checks local and deterministic.

#### `purchase_access`

- Requires buyer signer.
- Verifies registry not paused, commitment active, sale active, clock in range, requested tier enabled, occupied seats below max, correct treasury, and canonical grant PDA.
- Computes price and expiry from Sale; buyer cannot supply either.
- Invokes System Program transfer for exact lamports.
- Initializes AccessGrant and increments occupied seats using checked arithmetic.
- Emits `AccessPurchased`.

Because all instructions are in one Solana transaction, a failed transfer, grant initialization, or seat increment rolls back the whole purchase.

#### `set_dataset_status` and `set_sale_status`

- Publisher/authority only.
- Permit explicit forward state transitions.
- Never mutate commitment hashes or reduce occupied seats.

#### `revoke_access`

- Registry authority only; permits `ACTIVE → REVOKED` and no reverse transition.
- Does not decrement occupied seats and does not imply an automatic refund.
- Requires an audited off-chain reason; any refund policy must be handled explicitly outside the V1 purchase instruction.

Sale and authority rules frozen for V1:

- Exactly one immutable Sale PDA is allowed per DatasetCommitment. A faulty sale is suspended and a new DatasetPackage/DatasetCommitment is published; a sale is not silently replaced.
- Ending/suspending a Sale never revokes grants already purchased.
- `grant_duration = 0` is invalid rather than meaning unlimited access.
- Timestamp-plus-duration, prices, and seat arithmetic use checked operations.
- Delayed release is anchored to DatasetCommitment `created_at`.
- Dataset version monotonicity is enforced by the publisher service/database and audited signer intent; on-chain V1 guarantees uniqueness through the versioned PDA but does not independently prove there are no skipped version numbers.
- Registry authority/treasury rotation is either implemented as an explicit current-authority-signed instruction with an event and tests, or declared unsupported in the Solana ADR. It is never changed through client-provided unchecked accounts.
- Program events are indexes/audit aids, not authorization authority.

## 10. Wallet authentication and buyer transaction flow

### 10.1 SIWS flow

1. Frontend connects a Wallet Standard-compatible wallet.
2. `POST /api/v1/auth/siws/challenge` creates a random single-use nonce and returns domain, address, statement, URI, version, chain ID, issued time, and expiry.
3. Wallet signs through SIWS; legacy wallets sign the exact server-provided message.
4. `POST /api/v1/auth/siws/verify` validates message bytes, Ed25519 signature, address, nonce, domain, URI, chain, issued time, expiry, and nonce unused state.
5. In one transaction the server consumes the nonce, upserts UserWallet, and creates a hashed HTTP-only session.
6. Session middleware attaches the verified wallet address. Public-key request parameters never override it.

### 10.2 Purchase flow

1. Frontend reads public package/sale data from the API; API decodes fresh chain accounts.
2. `POST /api/v1/sales/:salePda/purchase-transaction` validates the wallet session and returns a short-lived unsigned transaction bound to the session wallet, dataset, sale, tier, treasury, recent blockhash, and configured program.
3. Browser wallet reviews, signs, and sends the transaction.
4. Frontend posts only the signature to `POST /api/v1/purchases/confirm`.
5. Backend calls `getTransaction`, requires a confirmed non-null result with `meta.err = null`, validates program/accounts/instruction, and reads the resulting AccessGrant PDA.
6. Reconciler stores an immutable Purchase row plus cache/audit events. The UI may show `PAYMENT_OBSERVED` after confirmed decoding, but access remains locked.
7. Only after the transaction and resulting grant/sale accounts are `finalized` does the purchase become `ACCESS_READY`.

Do not trust transfer amount or recipient inferred from client input. The program selects the exact `u64` price from Sale; the client does not supply an amount. Validate the finalized transaction's configured program, canonical sale/commitment/grant/treasury, buyer signer, decoded tier, CPI transfer, resulting Sale seat state, and AccessGrant fields. Insufficient balance, wrong treasury/account substitution, or any mismatch fails the purchase.

## 11. Protected delivery and tier enforcement

Required routes:

- `GET /api/v1/dataset/:packageId/metadata?version=N`
- `GET /api/v1/dataset/:packageId/report?version=N`
- `GET /api/v1/dataset/:packageId/data?version=N`
- `GET /api/v1/dataset/:packageId/export?version=N`

Here `packageId` is a version-scoped opaque public identifier that resolves to exactly one purchased DatasetCommitment. It is never the logical dataset ID. The optional requested version is constrained by that commitment and its tier policy for all four routes; omitting it selects the newest authorized version, not the globally newest dataset version.

Authorization algorithm:

1. Require a valid wallet session.
2. Resolve `packageId` through a uniqueness constraint to exactly one DatasetCommitment; reject zero or multiple matches and never accept an object key from the client.
3. Derive AccessGrant PDA from configured program ID, commitment PDA, and session wallet.
4. Read the account at `finalized` commitment for delivery authorization.
5. Verify owner, discriminator, PDA, dataset commitment, wallet, active status, tier, and expiry.
6. Load the purchased package policy artifact, verify its hash and exact field mapping against DatasetCommitment/Sale, then compute the authorized commitment/version for the grant tier and current time.
7. Resolve the selected version to its own sealed DatasetPackage and read that package's DatasetCommitment at `finalized`. Require the same dataset ID hash, exact selected version, active status, matching artifact hashes, and a completed sealed AnalysisRun.
8. Resolve an allowlisted artifact role (`metadata`, `report`, `data`, `export`) from the selected version's package record. If that older/current version has no sealed committed package or required report artifact, deny the role; never fall back to the purchased version's artifact.
9. Stream bytes through the backend with range/size/rate controls; V1 does not issue storage signed URLs.
10. Write an audit event before/after delivery with purchased package, selected package/version, grant, and role, without logging plaintext or internal object keys.

A merely confirmed purchase is visible as pending and cannot authorize bytes. RPC disagreement or inability to prove finality returns 503; the database cache never becomes a fallback authority.

Tier behavior:

- The canonical V1 access-policy artifact includes `policy_version`, `grant_scope`, `allowed_tier_mask`, `early`, `delayed.version_lag`, `delayed.release_seconds`, and `expiry.grant_duration_seconds`. Its exact bytes are hashed into `access_policy_hash`; the hash and every authorization-relevant primitive, including grant duration, are stored in DatasetCommitment.
- `grant_scope` is `PURCHASED_DATASET_LINE`: the grant records dataset ID hash and purchased version. It cannot cross into another logical dataset.
- Early grant: `max_visible_version = purchased_version` immediately.
- Delayed grant: before `commitment.created_at + delayed_release_seconds`, the newest visible version is the Sale's validated `delayed_initial_commitment` at `purchased_version - delayed_version_lag`; afterward it becomes the purchased DatasetCommitment/version.
- Enabling Delayed requires that the older version already has a sealed package and finalized active DatasetCommitment with metadata/report/data/export artifacts appropriate for sale.
- Publisher signer decodes the policy artifact and requires field-for-field equality between its allowed-tier mask/version lag/release seconds/expiry bounds, DatasetCommitment primitives, and Sale tier/duration fields before signing. Backend authorization repeats these equality checks after verifying `access_policy_hash`. Any conflict fails closed.
- The listing endpoint must exclude unavailable versions, and the object endpoint must repeat the same check to prevent URL/ID bypass.

## 18. Migration and rollout strategy

### Stage A — Additive shadow mode

- Add PostgreSQL/object storage/queue without removing the encrypted store.
- New workflow writes only to the new stack; legacy reads remain available.
- Import existing metadata as explicitly labeled legacy records.
- Compare API views and counts; do not dual-author mutable records.

### Stage B — Owner workflow cutover

- Route discovery/scrape/analysis through durable jobs.
- Keep old routes as adapters.
- Freeze encrypted state to read-only after a backup and reconciliation report.

### Stage C — Marketplace launch on Devnet

- Enable package publication only for new sealed AnalysisRuns.
- Allowlist configured program/network and one publisher authority.
- Release wallet auth and purchase to a small internal cohort.

### Stage D — Demo readiness

- Pre-fund publisher, treasury-test, buyer, and second unauthorized wallets.
- Pin a stable Devnet RPC and verify fallback endpoint.
- Run the complete scenario before the event without reusing its dataset artifacts as fake live ingestion.
- Keep a transparent external-dependency status page in the operator screen.

Rollback rules:

- Off-chain API/worker releases may roll back while preserving migrations and immutable artifacts.
- Published DatasetCommitments are never rolled back or mutated; disable/suspend through explicit program status if required.
- A faulty sale is closed/suspended through allowed state transition and replaced; never rewrite its account history.
- Do not restore an old database snapshot as if it were current without chain reconciliation.

## 19. Test strategy

### 17.1 Unit tests

- URL canonicalization and SSRF policy.
- Parser bounds and hostile payloads.
- Schema/frequency/unit inference.
- Canonical serialization and cross-language hash fixtures.
- Signal transforms and lag alignment.
- Split/purge/embargo logic.
- Every score component and cap/penalty.
- PDA derivation, account validation helpers, tier policy, and nonce verification.

### 17.2 Integration tests

- PostgreSQL uniqueness/transactions/migrations.
- Object put-once, storage-side encryption, private ACL, and authorized backend streaming.
- Queue retry, lease expiry, deduplication, and crash recovery.
- HTTP fetch → raw snapshot → normalized version.
- Analysis manifest → identical re-run hash.
- Local-validator program transactions and seat/grant constraints.
- Backend AccessGrant read and protected endpoint authorization.

### 17.3 Contract tests

- OpenAPI request/response schemas.
- Rust ↔ TypeScript instruction serialization.
- Rust ↔ TypeScript PDA and hash fixtures.
- Program ID/IDL consistency.
- Marketplace response values match decoded accounts.

### 17.4 Security tests

- SIWS nonce replay, phishing-domain mismatch, wrong address/chain, expiry.
- CSRF for owner mutations; session fixation/rotation.
- IDOR across dataset/package/version/object key.
- Wrong program owner, fake account data, wrong PDA, stale/failed transaction.
- Sold-out race and duplicate purchase.
- Object-key non-disclosure, unauthorized streaming, and range-request limits.
- Source prompt injection and malicious CSV/JSON/HTML.

### 17.5 Live acceptance tests

Run separately with explicit credentials/network flags. They must prove real HTTP provider responses and real Devnet transactions. Network failure produces `UNAVAILABLE`, never synthetic success.

## 20. Observability and operations

Metrics:

- discovery candidates/duplicates by provider;
- scrape latency/status/bytes/records/change type/failure streak;
- normalization and analysis duration;
- queue depth, lease age, retries, dead letters;
- dataset versions and package-gate rejection reasons;
- Solana RPC latency/errors, transaction confirmations, reconciliation lag;
- purchase attempts/success/failure by safe error code;
- protected access allowed/denied and download bytes;
- proof verified/mismatch/unavailable.

Logs carry request/job/analysis/package IDs but never raw data, exact private URLs, object keys, cookies, nonces, signatures of off-chain auth messages, or secret keys.

Alerts:

- source broken beyond threshold;
- worker heartbeat missing;
- queue lease/dead-letter growth;
- artifact hash mismatch;
- chain cache divergence;
- signer policy rejection spike;
- sale occupied seats exceeding/max mismatch (critical invariant);
- protected authorization errors or unexpected 2xx for negative probes.
