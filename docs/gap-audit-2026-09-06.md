# QARAU MVP — independent gap audit

**Date:** 2026-09-06
**Audited state:** working tree at commit `b5a0ec3` plus uncommitted changes (45 dirty paths).
**Method:** requirement-by-requirement verification of the 25 requirements in
`QARAU_MVP_INTEGRATION_PLAN.md` §15 against the code, the schema, and executed test runs.
No claim below is taken from `QARAU_MVP_IMPLEMENTATION_STATUS.md` or
`docs/proofpilot-review.md` — both are treated as assertions to be checked.

**Note on volatility:** `server/jobs/handlers/chain-publish.mjs` and
`server/test/release-regressions.test.mjs` changed during this audit. An earlier
integration run failed `release-regressions.test.mjs:32`; after the edit it passes.
Findings below reflect the tree as of the final verification pass.

## Verdict

The off-chain pipeline (discovery → ingestion → immutable versions → quantitative
validation → package sealing) is genuinely implemented and tested. The on-chain
*write* path is implemented. The gaps cluster in three places:

1. **No reconciliation loop.** On-chain state is written once at publish and never read
   back. Everything downstream of that — seat counts, sale liveness, grant lifecycle — is
   frozen at publish time.
2. **No program-behavior tests.** All six Rust tests exercise pure functions. Not one
   instruction is tested, including the seat cap and the payment transfer.
3. **Two live owner-writable stores.** The legacy encrypted-file API is still mounted in
   integrated mode.

Requirements 15, 16 and 24 cannot be called met on evidence. Requirement 5 is not
implemented in the production runtime at all.

### F-01 — Seat occupancy is never refreshed (High)

`chain-publish.mjs:30` writes the sale row with a hardcoded `occupied_seats: 0`:

```js
{ treasury: published.treasury, starts_at: startsAt, ends_at: endsAt,
  early_price_lamports: ..., delayed_price_lamports: ..., occupied_seats: 0 }
```

`v1.mjs:49` serves that value to the public marketplace, and `Marketplace.tsx:62` renders
`{item.max_seats - item.occupied_seats} / {item.max_seats} seats remaining`. Grepping the
whole server for `occupied_seats` returns exactly two writers — both the literal `0` above —
and one reader. Nothing ever reads `Sale.occupied_seats` back from the chain.

**Consequence:** the marketplace advertises a fully-available sale forever. When the cap is
actually reached, the program correctly returns `SeatsExhausted`, so the buyer discovers it
only after signing a transaction in their wallet. Requirement 15's on-chain half is
implemented; its user-visible half is wrong by construction.

**Fix:** decode `Sale` from chain (the layout is already in
`canonical-artifacts.mjs:SOLANA_ACCOUNT_LAYOUTS.Sale`) and refresh `sales.decoded_state`
before serving `/marketplace` and `/packages/:id/public`, or on the reconcile loop of F-02.

### F-02 — `chain.reconcile` is declared but not wired (High)

`payloads.mjs:13` defines the job type with a role and a strict schema:

```js
"chain.reconcile": Object.freeze({ role: "worker-chain", version: 1,
  schema: z.object({ network: z.enum(["localnet","devnet"]), account: nonempty }).strict() }),
```

`worker-entry.mjs` registers only `chain.publish` for `worker-chain`. Grep across the
server for `chain.reconcile` returns that one declaration and nothing else — no handler,
no producer, no scheduler entry.

Three schema columns exist solely to serve this loop and are therefore dead:

- `sales.stale_after` — written as `now() + interval '5 minutes'` at publish, never read.
- `sales.last_reconciled_at`, `blockchain_commitments.last_reconciled_at` — set at publish, never advanced.

**Consequence:** this is the root cause of F-01, and it means a sale that was closed,
paused, or exhausted on chain is indistinguishable from a live one in the database.
Requirement 13's evidence line ("Decoded Devnet DatasetCommitment") holds only for the
instant of publication.

### F-03 — Kill-switch and sale closure are unreachable (High)

The program implements both:

- `set_paused` — `programs/qarau_registry/src/lib.rs:36`
- `close_sale` — `programs/qarau_registry/src/lib.rs:194`

`registry.paused` is enforced in `create_dataset_commitment` and in `purchase`
(`lib.rs:100`, `lib.rs:289`). But `publisher.mjs` builds only three instructions —
`initialize`, `create_dataset_commitment`, `create_sale` — and a grep for `set_paused` /
`close_sale` across all `.mjs` returns nothing outside the Rust source.

**Consequence:** the emergency stop exists on chain and cannot be pulled from the product.
Stopping a live sale requires an out-of-band `anchor`/CLI invocation with the upgrade
authority, which the plan explicitly says must never be mounted into an application
container (`docs/runtime/services.md`). There is no documented operator runbook for this.

### F-04 — No instruction-level program tests (Medium)

Total Rust tests: 6.

| File | Tests | What they cover |
|---|---|---|
| `contracts.rs` | 4 | access-policy / analysis-manifest / dataset-id hash fixtures, frozen account spaces |
| `lib.rs` | 2 | `validate_commitment` accept + reject — a pure function |

There is no `tests/` directory, no `litesvm` / `solana-program-test` harness, and no
TypeScript Anchor test. Consequently **none** of the following is verified anywhere:

- purchase at `occupied_seats == max_seats` fails (`SeatsExhausted`) — the exact evidence
  requirement 15 demands: *"Final seat succeeds; next purchase fails"*
- purchase outside `[starts_at, ends_at]` fails
- purchase with a treasury other than `Registry.treasury` fails
- the SOL transfer amount matches the tier price — requirement 16's *"Confirmed real SOL transfer and atomic grant"*
- `paused` blocks a purchase
- a second `purchase` by the same wallet fails on the `AccessGrant` PDA init

Plan §9.3 ("Program tests") is unmet. This is the single largest evidence gap in the audit:
the money-handling instruction has zero automated coverage.

### F-05 — Treasury defaults to the hot publisher key (Medium)

`publisher.mjs:44`:

```js
const treasury = input.treasury ?? signer.address;
```

`chain-publish.mjs` builds `input` with fourteen fields and `treasury` is not among them,
so the fallback always applies. `initialize` then writes that address into
`Registry.treasury`, which has no setter — it is fixed for the life of the registry
(`lib.rs:22`).

**Consequence:** every buyer's SOL lands on the same key that signs publications, i.e. the
operational hot key running inside `publisher-signer`. There is no separation between
signing authority and revenue custody, and it cannot be corrected after `initialize`
without deploying a new registry. On Devnet this is harmless; the same code path on any
real network is not.

**Fix (cheap, before the live registry is initialized):** thread a `TREASURY_ADDRESS`
through `chain-publish.mjs` into `input.treasury` and make `publisher.mjs` throw instead of
falling back.

### F-06 — Legacy API stays mounted in integrated mode (Medium)

`index.mjs:89` guards only the durable router:

```js
if (runtimeConfig.runtimeMode === "integrated") { app.use("/api/v1", createV1Router({...})); }
```

`app.use("/api/research", research)` (`index.mjs:266`) and `app.use("/api/qarau", qarauApi)`
(`index.mjs:314`) are unconditional. Both routers sit behind the same `requireOwner` +
`requireCsrf` as `/api/v1`, and both write to the AES-encrypted prototype store via
`QarauService`.

`QARAU_MVP_IMPLEMENTATION_STATUS.md` states *"The legacy pages are no longer reachable from
owner navigation or routes."* That is accurate for the React app — `App.tsx` imports none
of the legacy pages, verified — but it is not true of the HTTP surface. A single owner
session can still mutate two independent stores, including `POST /api/qarau/sources/:id/analyze`,
which runs the external-AI path.

**Fix:** wrap both mounts in `if (runtimeConfig.runtimeMode === "legacy")`, or delete them
as part of the Stage-C cutover in plan §18.

### F-07 — The AI layer is absent from the production runtime (Medium)

`analyzeSource` / `analyzerConfig` (`server/analyzers/index.mjs`) are imported by exactly
one non-test file: `server/qarau-service.mjs:10`. The `/api/v1` router has no semantic
analysis endpoint, no `AI_*` configuration read, and no column populated from an analyzer.
The `analysis_runs` table is purely quantitative.

Requirement 5 reads: *"AI layer — INT-020, INT-030, INT-034 — Strict AI schema; score
remains numeric-only."* The second half is satisfied trivially (there is no AI to
contaminate the score). The first half is not implemented on the path that ships.

The analyzer itself is well built — strict key-set equality, control-character stripping,
`AI_SAFE` projection, fail-closed on non-public sources, untrusted-content framing — and
`security-boundaries.test.mjs` covers it. It is simply not connected to anything the
integrated product runs.

**Decide explicitly:** either port it into a `analysis.semantic` job for `/api/v1`, or
strike requirement 5 from the plan. Leaving it half-migrated is the worst option, because
the legacy endpoint that *does* invoke it is still reachable (F-06).

### F-08 — Production signer lacks the controls the docs describe (Medium)

Two signer implementations exist:

| Path | Used by | Controls |
|---|---|---|
| `signer/devnet-signer.mjs` + `signer/policy.mjs` | legacy `QarauService` child process | exact `{action,epoch,root,version}` shape, `COMMIT_MERKLE_ROOT` only, 24 tx/day (`policy.mjs:8`), Memo-program allowlist |
| `signer/server.mjs` + `signer/publisher.mjs` | **`worker-chain` — the production path** | bearer token, 8 KB body cap, devnet RPC regex, 32-byte hash length checks |

`validateIntent` and `enforceDailyLimit` are imported only by `devnet-signer.mjs` and the
test. The production `/publish` endpoint has **no daily transaction limit and no action
allowlist** — it will build whatever `initialize` / `create_dataset_commitment` /
`create_sale` sequence the caller's payload implies, for any dataset hash, unbounded.

Meanwhile `README.md:148` states *"The signer is Devnet-only, Memo-program allowlisted,
limited to 24 transactions/day"* and `SECURITY.md:30` describes the child-process intent
model. Both describe the legacy signer. A reader auditing the security posture will
conclude controls exist that do not exist on the deployed path.

**Fix:** either port `enforceDailyLimit` and an instruction allowlist into
`publisher.mjs`, or correct both documents to describe the actual production boundary.
The token + network pin is a real boundary; it is just narrower than advertised.

### F-09 — `schedule.due-sources` is a dead contract entry (Low)

Declared at `payloads.mjs:14` with role `scheduler`. The scheduler
(`enqueue-due-sources.mjs:19`) enqueues `scrape.source` jobs directly and never emits its
own job type. Harmless, but `jobTypesForRole("scheduler")` returns a type no worker
handles, which will mislead the next person wiring a scheduler worker.

### F-10 — `pipeline_stage_runs` is unused (Low)

Created at `0001_initial.sql:426` with the `pipeline_stage` enum (10 values). Grep across
`server/` and `src/` returns no reference outside the migration. Either the per-stage
timing telemetry was dropped, or it was never implemented.

### F-11 — `access_grant_cache` is written but never read (Low)

Written on purchase confirmation (`v1.mjs:261`). Protected delivery deliberately reads the
grant from chain on every request (`v1.mjs:269` → `readAccessGrant`), which correctly
enforces `status == 1` and `expiresAt > now` at `registry-client.mjs:93`. **Grant expiry is
properly enforced** — that is a genuine strength, not a gap.

The gap is that the cache table is write-only and unmaintained: nothing ever flips a row to
expired or revoked, so any future feature that trusts it (an owner-facing buyer list, an
analytics view) will read stale rows. Either drive it from the reconcile loop of F-02 or
drop the table.

### F-12 — Dead legacy page components (Low)

`src/pages/Discovery.tsx`, `Signals.tsx`, `SignalDetail.tsx`, `Data.tsx`, `Runs.tsx`,
`SourceDetail.tsx` are imported by nothing (verified by grep). They are not bundled, but
they still typecheck under `tsc -b`, still get linted, and they still call legacy
`/api/qarau` endpoints, which makes them look supported. Delete them with F-06.

### F-13 — `npm test` hides the PostgreSQL suite (Low)

Measured, not asserted:

| Command | tests | pass | skip |
|---|---|---|---|
| `npm test` | 69 | 64 | **5** |
| `npm run test:integration` | 69 | 69 | 0 |

The five skipped tests are the entire database-backed layer — migrations, repository
invariants, queue semantics, scrape/discovery/analysis handlers. `npm test` is the
documented default and it exits 0 with a clean-looking summary. Anyone running it without
Docker gets a false green on the persistence layer.

`package.json` should make `test` the integration runner, or `test` should print a warning
when `TEST_DATABASE_URL` is absent.

## What this audit did not verify

- **Live Devnet state.** No RPC calls were made. Whether `Registry` is initialized, whether
  any `DatasetCommitment` or `Sale` exists on Devnet, and whether the deployed bytecode
  matches `programs/qarau_registry/` were not checked.
- **`cargo test` execution.** Test *count* and *content* were read from source; the suite
  was not run in this session.
- **The production container.** All runs were on the host, not inside the runtime image.
- **Browser behavior.** No page was loaded; frontend findings are from source only.

## Suggested order of work

1. F-01 + F-02 together — one `chain.reconcile` handler fixes the seat lie, the stale sale
   state and the dead `stale_after`/`last_reconciled_at` columns.
2. F-05 — must be settled *before* the live registry is initialized; it is one-way after.
3. F-04 — add a `litesvm` harness and test the seat cap, the sale window, the treasury
   binding and the pause. This is what turns requirements 15 and 16 from claims into evidence.
4. F-06 + F-12 + F-07 — one cutover decision: retire the legacy surface, or port the
   analyzer to `/api/v1` and keep it.
5. F-03 and F-08 — operator controls and honest documentation.
6. F-13 — make the default test command tell the truth.
